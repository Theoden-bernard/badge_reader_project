\chapter{Méthodologie et organisation}

\section{Gestion de projet avec GitHub}

Cette section présente l’approche de gestion de projet adoptée, entièrement centralisée autour de l’écosystème GitHub.  
L’objectif est d’assurer une planification claire, un suivi précis de l’avancement et une traçabilité complète des développements, de la conception jusqu’à la livraison.
\newline

Les outils GitHub sont utilisés à la fois comme support de collaboration, de gestion des tâches et de contrôle qualité, garantissant une organisation structurée et évolutive du projet.
\newline

\begin{for_you}{Mon approche GitHub :}
    \textit{
    GitHub est utilisé comme dépôt central du code source et de la documentation.  
    GitHub Projects permet de piloter l’organisation du travail via un tableau Kanban, tandis que GitHub Actions est exploité pour automatiser certaines tâches, telles que les vérifications ou les processus liés à l’intégration continue.
    }
\end{for_you}

\subsection{User Stories et estimation de temps}

Cette sous-section détaille les User Stories du projet ainsi que leurs estimations de temps.  
Chaque User Story est associée à des commits, des issues et des jalons (milestones) GitHub, assurant un suivi précis de l’avancement et une traçabilité complète des fonctionnalités développées.
\newline

\begin{for_you}{Kanban :}
    \begin{verbatim}
    https://github.com/users/Theoden-bernard/projects/2/views/2
    \end{verbatim}

    \textbf{Colonnes du tableau Kanban :}
    \begin{itemize}
        \item \textbf{Backlog :} Ensemble des fonctionnalités et tâches identifiées, non encore planifiées.
        \item \textbf{Ready :} Tâches prêtes à être intégrées dans le sprint suivant.
        \item \textbf{In Progress :} Tâches en cours de développement (limite de travail en cours — WIP — fixée à 3).
        \item \textbf{In Review :} Code développé en attente de relecture et de validation.
        \item \textbf{Done :} Fonctionnalités finalisées, testées et livrées.
    \end{itemize}
\end{for_you}

\section{Versioning GitHub et conventions}

Le versioning du projet repose sur le modèle Git Flow, qui permet de structurer le développement à l’aide de branches dédiées à chaque type de travail.  
Cette organisation garantit une séparation claire entre le code stable, le code en cours de développement et les correctifs urgents.

Les conventions mises en place concernent le nommage des branches, le format des messages de commit et l’utilisation systématique des Pull Requests.  
Elles facilitent la traçabilité des évolutions, la relecture du code et l’intégration des fonctionnalités avant leur déploiement.
\begin{for_you}{Normes GitHub}
    \textbf{Schéma Git Flow :}
    \begin{verbatim}
    main -----------------------------------------------
    |
    +-- develop --------------------------------------
        |
        +-- feature/user-authentication
        +-- feature/project-management
        +-- hotfix/critical-bug-fix
    \end{verbatim}

    \textbf{Conventions de commit :}
    \begin{lstlisting}
    FEAT: add user authentication system
    FIX: resolve login validation issue
    DOCS: update documentation
    TEST: add unit tests for user service
    REFACTOR: improve code structure
    \end{lstlisting}

    \textbf{Pull Requests :}
    \begin{itemize}
        \item Toute nouvelle fonctionnalité ou correction est intégrée via une Pull Request.
        \item Une revue de code est effectuée avant toute fusion dans la branche \texttt{develop}.
        \item Les Pull Requests doivent respecter les conventions de commit et décrire clairement les changements apportés.
    \end{itemize}
\end{for_you}

\section{Planification et outils de suivi}
La planification du projet s’appuie sur une combinaison complémentaire d’outils GitHub, permettant d’aligner vision stratégique et exécution opérationnelle. La roadmap GitHub offre une vue macro du projet en mettant en évidence les grandes phases, les jalons clés et les dépendances majeures, tandis que GitHub Projects est utilisé comme outil de pilotage quotidien via une approche Kanban.
Cette organisation à deux niveaux permet de conserver une vision claire des objectifs à long terme tout en assurant un suivi précis de l’avancement des tâches. La roadmap facilite la communication des priorités produit et la gestion des risques de planning, tandis que GitHub Projects optimise la répartition du travail, la collaboration entre les développeurs et la réactivité face aux imprévus.
\newline

\begin{for_you}{Roadmap GitHub}
    \begin{verbatim}
    Phase 1: Conception (4 semaines)
    +-- Analyse des besoins (1 semaine)
    +-- Conception technique (2 semaines)
    +-- Validation de l’architecture (1 semaine)

    Phase 2: Développement MVP (8 semaines)
    +-- Base de données (L)
    +-- Authentification (S)
    +-- Frontend Phoenix (S)
    +-- Système de badge (L)
    \end{verbatim}

    \textbf{\newline Configuration de GitHub Projects :}
    \begin{itemize}
        \item \textbf{Colonnes :} Backlog, To Do, In Progress, Review, Done
        \item \textbf{Limites WIP :} maximum 3 tâches simultanées par développeur
        \item \textbf{Règles :} Pull Request obligatoire avant toute fusion dans la branche \textit{develop}
        \item \textbf{Automatisation :} mise à jour automatique des statuts en fonction de l’avancement
    \end{itemize}
\end{for_you}
