\chapter{Architecture MVC Monolithique}

\section{Architecture MVC Monolithique}

\textbf{Mon architecture monolithique :} 
s'appuie sur la pile \textbf{Elixir/Phoenix} pour centraliser l'interface et la logique métier. Ce choix permet de bénéficier de :
\begin{itemize}
    \item Une application web \textbf{modulaire, moderne et performante}.
    \item Une gestion native du \textbf{temps réel} et de la \textbf{concurrence} sans multiplier les serveurs.
\end{itemize}

\subsection{L'interface utilisateur (Vue et Contrôleur)}

\begin{for_you}{Technologies de présentation et Structure du projet :}
    \textbf{Technologies de l'interface :}
    \begin{itemize}
        \item \textbf{Framework} : Phoenix 1.8.0 + \textbf{LiveView} 1.1 (Gestion de l'interface côté serveur).
        \item \textbf{Gestion d'état} : Socket LiveView, GenServer et ETS (Erlang Term Storage).
        \item \textbf{Moteur de rendu} : HEEx (HTML + Elixir Expressions).
        \item \textbf{Routing} : Pipeline Plug (gestion native des requêtes HTTP).
        \newline
    \end{itemize}

    \textbf{Structure des répertoires :}
    \begin{verbatim}
    badge_reader/
    +-- _build/                            # Compilation du projet
    +-- assets/                            # CSS et JavaScript statique
    +-- config/                            # Configuration par environnement
    +-- deps/                              # Dépendances (Mix)
    +-- lib/                               # Code source global
    |   +-- badge_reader/                  # Partie "Modèle" et Logique métier
    |   +-- badge_reader_web/              # Partie "Vue" et "Contrôleur"
    |   +-- badge_reader_web.ex            # Point d'accès Web
    |   +-- badge_reader.ex                # Point d'accès Métier
    +-- priv/                              # Migrations SQL et assets privés
    +-- test/                              # Tests automatisés
    \end{verbatim}
\end{for_you}

\subsection{La Logique Métier (Modèle et Contextes)}

\textbf{Organisation de la logique métier :\newline} 
\begin{for_you}{Environnement Mix et modularité}
    \textbf{Mix} gère l'ensemble du cycle de vie du monolithe :
    \begin{itemize}
        \item La \textbf{compilation} unique de toutes les couches.
        \item La gestion des \textbf{dépendances} via Hex.pm.
        \item L'\textbf{isolement des domaines} via les Contextes :
              \begin{itemize}
                  \item \texttt{lib/badge\_reader/} : Contient les règles métier pures.
                  \item \texttt{lib/badge\_reader\_web/} : Contient la logique de présentation.
              \end{itemize}
    \end{itemize}
\end{for_you}

\subsubsection{Le Contrôleur (ou LiveView)}

\begin{for_you}{Exemple de contrôleur Phoenix}
    \begin{lstlisting}
    # lib/badge_reader_web/controllers/badge_reader_controller.ex

    defmodule BadgeReaderWeb.BadgeReaderController do
        use BadgeReaderWeb, :controller

        def login_page(conn, _params) do
            render(conn, :login_page)
        end

        def dashboard(conn, _params) do
            render(conn, :dashboard)
        end
    end

    \end{lstlisting}
    
    \textit{Rôle} :
    \begin{itemize}
        \item \textbf{LiveView} : Remplace souvent les contrôleurs classiques pour un état persistant.
        \item \textbf{HEEx} : Permet de construire l'interface dynamiquement.
        \item \textbf{Router} : Centralise l'aiguillage des requêtes utilisateur.
    \end{itemize}
\end{for_you}

\subsubsection{Le Contexte (Logique Métier)}

\textbf{Mes Contextes :} Au lieu de "Services" externes, Phoenix utilise des contextes pour encapsuler la logique.
\newline

\begin{for_you}{Exemple de contexte métier :}
    \begin{lstlisting}
    # lib/badge_reader/access_control.ex
    defmodule BadgeReader.AccessControl do
    alias BadgeReader.Repo
    alias BadgeReader.AccessControl.Badge

    def create_badge(attrs \\ %{}) do
        # Logique métier : validation puis insertion
        %Badge{}
        |> Badge.changeset(attrs)
        |> Repo.insert()
    end
    end
    \end{lstlisting}
\end{for_you}

\subsection{Couche Données (Database)}

\begin{for_you}{Architecture des données au sein du monolithe}
    \textbf{Technologies utilisées} :
    \begin{itemize}
        \item \textbf{PostgreSQL} : Base de données robuste pour la persistance.
        \item \textbf{Ecto} : ORM pour Elixir (requêtes typées, migration).
        \newline
    \end{itemize}

    \textit{Exemple de schéma Ecto (User)} :
    \begin{lstlisting}
    # lib/badge_reader/user.ex

    defmodule BadgeReader.Accounts.User do
        use Ecto.Schema
        import Ecto.Changeset

        schema "users" do
            field :email, :string
            field :password, :string, virtual: true, redact: true
            field :hashed_password, :string, redact: true
            field :confirmed_at, :utc_datetime
            field :authenticated_at, :utc_datetime, virtual: true

            timestamps(type: :utc_datetime)
        end
        ...
    end
    \end{lstlisting}

    \textit{\newline Exemple de migration} :
    Elles servent d'historique de version pour la base de données, permettant de créer ou modifier les tables de manière reproductible et sécurisée sur n'importe quel environnement.
    \begin{lstlisting}
    # priv/repo/migrations/20260128141856_create_users.exs

    defmodule BadgeReader.Repo.Migrations.CreateUsers do
        use Ecto.Migration

        def change do
            create table(:users) do
            add :first_name, :string
            add :last_name, :string
            add :email, :string
            add :password, :string
            end
        end
    end

    \end{lstlisting}
\end{for_you}

\subsection{Communication entre les composants du Monolithe}

Dans cette sous-section, nous détaillons comment les couches communiquent de manière fluide au sein de la machine virtuelle Erlang (BEAM).
\newline

\begin{for_you}{Flux de communication interne :}

\textbf{L'architecture Monolithique avec Phoenix est particulièrement efficace car :\newline}
    \begin{itemize}
        \item \textbf{Pas de latence réseau} : Contrairement à une architecture éclatée, les appels entre l'interface et la base de données se font en mémoire.
        \item \textbf{Cohérence forte} : Le backend et le frontend partagent les mêmes types de données et le même langage.
        \item \textbf{LiveView} : Réduit drastiquement la complexité en éliminant le besoin d'une API JSON intermédiaire.
        \newline
    \end{itemize}

\subsection{Avantages de l'architecture MVC Monolithique}

\begin{for_you}{Pourquoi ce choix ?}
    \begin{itemize}
        \item \textbf{Simplicité de déploiement} : Un seul artefact à déployer sur une instance EC2.
        \item \textbf{Maintenance centralisée} : Tout le projet est contenu dans un seul dépôt GitHub.
        \item \textbf{Temps de réponse} : L'absence de requêtes HTTP entre le front et le back garantit une fluidité maximale.
        \item \textbf{Sécurité} : Moins de surface d'attaque car il n'y a pas d'API publique exposée inutilement.
    \end{itemize}
\end{for_you}

\section{Développement de l'Interface (Front Office)}

\begin{for_you}{Mon approche avec LiveView}
    \textbf{Pourquoi LiveView ?}
    \begin{itemize}
        \item \textbf{Interactions temps réel} : Idéal pour voir instantanément un badge scanné sur le dashboard.
        \item \textbf{Zéro JS lourd} : Toute la logique d'interface est écrite en Elixir, simplifiant le débogage.
    \end{itemize}

    \textbf{Structure de la couche Web} :
    \begin{verbatim}
    lib/badge_reader_web/
    +-- components/      # Composants UI (boutons, cartes)
    +-- live/            # Pages LiveView interactives
    +-- controllers/      # Gestionnaires HTTP classiques
    +-- router.ex         # Définition des accès
    \end{verbatim}
\end{for_you}
